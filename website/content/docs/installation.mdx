title: Installation

`pm` ships as a single Go binary with no runtime dependencies. Pick the installation method that suits your environment.

<Callout type="info">
  **Prerequisites:** Release binary install requires the GitHub CLI (`gh`) and `tar`, but does not require Go. `go install` and source builds require Go 1.25.11 or later. Source builds also need a C toolchain (gcc or clang), because DuckDB is embedded in every build.
</Callout>

## Installation methods

<Tabs items={["Release binary", "go install", "Build from source"]}>

<Tab value="Release binary">

Release assets are published from [`polymetrics-ai/cli`](https://github.com/polymetrics-ai/cli/releases) for Linux and macOS on amd64 and arm64.

<Callout type="info">
  **Windows is not published.** `windows/arm64` has no prebuilt DuckDB library and cannot be built at all; `windows/amd64` was dropped because pm has no Windows user asking for it. Both return if someone does — `pm` still builds from source on Windows amd64 with a C toolchain. Use WSL in the meantime.
</Callout>

This path requires the GitHub CLI (`gh`) and `tar`, but does not require Go.

```bash
os_name="$(uname -s)"
arch_name="$(uname -m)"

case "$os_name" in
  Darwin) os=darwin ;;
  Linux) os=linux ;;
  *) echo "unsupported OS: $os_name" >&2; exit 1 ;;
esac

case "$arch_name" in
  x86_64|amd64) arch=amd64 ;;
  arm64|aarch64) arch=arm64 ;;
  *) echo "unsupported architecture: $arch_name" >&2; exit 1 ;;
esac

tmpdir="$(mktemp -d)"
trap 'rm -rf "$tmpdir"' EXIT
gh release download --repo polymetrics-ai/cli --pattern "pm_*_${os}_${arch}.*" --dir "$tmpdir"

tar -xzf "$tmpdir"/pm_*_"${os}"_"${arch}".tar.gz -C "$tmpdir"
binary_name=pm

install_dir="${INSTALL_DIR:-$HOME/.local/bin}"
mkdir -p "$install_dir"
cp "$tmpdir/$binary_name" "$install_dir/$binary_name"
chmod +x "$install_dir/$binary_name" 2>/dev/null || true
"$install_dir/$binary_name" version
```

Each release includes `checksums.txt` for artifact verification.

</Tab>

<Tab value="go install">

Use this path when your environment can resolve the `polymetrics.ai` module path.

```bash
go install polymetrics.ai/cmd/pm@latest
```

The binary is placed at `$GOPATH/bin/pm`. Make sure `$GOPATH/bin` (or `$(go env GOPATH)/bin`) is on your `$PATH`.

To pin a specific version replace `latest` with a version tag, for example `v0.9.0`.

</Tab>

<Tab value="Build from source">

Clone the repository and build locally:

```bash
git clone https://github.com/polymetrics-ai/cli
cd cli
make build        # produces ./pm  (requires a C toolchain for DuckDB)
make install      # copies ./pm to $GOPATH/bin
```

### Build requirements

DuckDB is embedded in every build -- it is the query engine and the only Parquet
implementation in the binary -- so building from source requires cgo and a C
toolchain (gcc or clang). There is no build flag and no CGO-free variant: two
builds that wrote different table formats would mean a query that works on one
install and fails on another.

<Callout type="warn">
  Cross-compiling to a different OS or architecture requires a matching C cross-toolchain. `pm` still has zero *runtime* dependencies -- no database, no cache, no network service -- which is unchanged.
</Callout>

</Tab>

</Tabs>

## Binary size profile

`pm` is still a single local binary. Production builds embed only rendered execution JSON: metadata, connection specs, streams, schemas, writes, operations, CLI surface, and optional sync transport and rate limits. Compact `source.lock.json` authoring records are never embedded or read by the runtime. Embedding DuckDB adds roughly 31 MiB, measured on darwin/arm64.

| Build mode | Measured size | Use |
|---|---:|---|
| Default local build | 137,779,042 bytes (131 MiB) | Developer builds with normal Go symbol/debug data. |
| Release-style stripped build | 111,479,570 bytes (106 MiB) | Recommended release profile: `go build -trimpath -ldflags="-s -w" ./cmd/pm`. |

Authoring inputs are intentionally left out of the shipping binary:

| Excluded artifact | Raw size | Why it is not embedded |
|---|---:|---|
| `source.lock.json` | Connector-dependent | Immutable provider facts used by `connectorgen lock-render`. |
| Provider fixtures | Connector-dependent | Optional local test inputs; never a second runtime route. |

`connectorgen lock-render` publishes a connector-local closed generation after
semantic staging validation; `connectorgen lock-render --check` verifies its
selected `CURRENT` generation without writing. This authoring foundation does
not materialize the checked-in corpus or change the execution-only runtime
reader. `connectorgen validate` validates only the execution bundle that the
runtime consumes. Release archives can be smaller or larger than the raw
executable depending on operating system, architecture, and archive compression.

## Release cadence

Release PRs are generated from Conventional Commits after changes land on `main`. A connector update such as `fix(github): repair pagination` produces a patch release. A new connector such as `feat(connector): add linear` produces a minor release. Breaking changes use `!` or a `BREAKING CHANGE:` footer; while pm is pre-1.0 they produce a minor release, and from `1.0.0` onward a major release.

## Verify your installation

```bash
pm --help
```

```bash
pm connectors list | head -10
```

If you see a list of connector names, pm is installed and ready.

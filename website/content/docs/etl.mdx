The `pm etl` command group has two lanes:

| Lane | Commands | Use |
|---|---|---|
| Direct connector operations | `pm etl check`, `pm etl catalog`, `pm etl read` | Preflight and connector development without creating a connection. |
| Configured syncs | `pm etl run`, `pm etl status` | Production-style extraction from a saved connection into a local table. |
| Closed GitHub transport | `pm etl transport github-issue-label`, approved `pm etl run` | One fixed two-action GitHub label destination from its definition-declared sources, through durable warehouse reopen and typed cleanup. |
| Closed PostgreSQL transport | `pm etl transport postgres-managed-target`, approved `pm etl run` | A definition-selected PostgreSQL or API source through the durable warehouse into a managed PostgreSQL target. |
| Declarative typed destination | `pm etl transport declarative-typed-destination`, approved `pm etl run` | A connection-persisted, definition-selected `writes.json` action through the durable warehouse; never a generic HTTP writer. |

Connector capabilities are inspectable through `pm connectors inspect`. Use the advertised streams, cursors, and primary keys before creating a long-running extraction.

## Direct connector operations

```bash
pm etl check --connector <name> [--config key=value] [--json]
pm etl catalog --connector <name> [--config key=value] [--json]
pm etl read --connector <name> [--stream stream] [--limit n] [--config key=value] [--json]
```

Examples:

```bash
pm etl check --connector sample --json
pm etl catalog --connector sample --json
pm etl read --connector sample --stream customers --limit 5 --json
```

For a connector that needs configuration:

```bash
pm etl catalog \
  --connector github \
  --config owner=OWNER \
  --config repo=REPO \
  --config public_access=true \
  --json
```

## How connections and sync modes work

A **connection** is the named pairing of a connector credential and a storage credential, with one or more configured streams. The sync mode is set at connection-creation time using `--sync-mode` -- it is not a flag on `pm etl run`.

```bash
pm connections create <name> \
  --source <connector>:<credential-name> \
  --destination <connector>:<credential-name> \
  --stream <stream-name> \
  --primary-key <field> \
  --cursor <field> \
  --sync-mode <mode> \
  --table <destination-table> \
  --destination-action <declared-action> \
  --transform-file transform-plan.json \
  --target-copy-workers <n>
```

### Sync modes

| Mode | Value | Description |
|---|---|---|
| Full refresh overwrite | `full_refresh_overwrite` | Re-extracts all records and replaces the output table. Default if `--sync-mode` is omitted. |
| Full refresh append | `full_refresh_append` | Re-extracts all records and appends them to the output table. |
| Full refresh overwrite deduped | `full_refresh_overwrite_deduped` | Replaces the output and deduplicates by the declared primary key. Requires a matching executor. |
| Incremental append | `incremental_append` | Extracts only records newer than the stored cursor value and appends them. |
| Incremental append deduped | `incremental_append_deduped` | Extracts newer records and deduplicates by the declared primary key. Requires a matching executor. |
| Incremental dedupe | `incremental_dedupe` | Retains one current record per declared primary key. Unsupported connector/mode pairs refuse before source I/O. |
| Incremental dedupe history | `incremental_dedupe_history` | Retains source versions with `_valid_from`, `_valid_to`, and `_is_current` fields. It requires declared primary-key and cursor fields. |

Incremental modes require a cursor. Deduped modes also require a primary key. A static connector advertises a mode only when the rendered execution bundle names the required fields and a registered executor implements it. Runtime preflight rejects incompatible source, destination, or mode combinations before source I/O.

### Closed typed transforms

`--transform-file` is an optional bounded JSON `TransformPlanV1`. `pm` checks
it against the source's typed catalog before it saves the connection, stores
only its normalized form and SHA-256 hash, and binds that hash into the
database plan, preview, and approval. The available operations are typed
projection/rename, timestamp and date values, checked integer
multiply-and-cast, uppercase, modulo, and a `not_equal` filter. It never
accepts arbitrary SQL.

For the eligible PostgreSQL-to-PostgreSQL `full_overwrite` transport, this
plan selects the Arrow/DuckDB/binary-COPY path. Its input-byte measurement is
the pre-transform projected source Arrow bytes; it excludes Parquet, pgwire,
target storage, and checkpoint bytes. The durable run record reports decimal
MB/s and MiB/s plus individual phase timings.

For that immutable transformed target, `--target-copy-workers` is saved on the
connection, defaults to `2`, and is constrained to `1..min(8, target-declared
pool maximum)`. The closed plan and preview report the saved value and the
declared maximum. It is not a per-run `--workers` override: this release keeps
one ordered COPY consumer, so a second COPY lane remains a separately measured
follow-on rather than an implied capability.

### Polling-watermark limits and eligibility

`polling_watermark` is a bounded keyset polling mechanism, not CDC or change
capture. It is never enabled by a connector capability string alone. A mode is
eligible only after runtime preflight accepts its rendered native source,
discovered catalog object, and destination binding with registered executors.

An executable binding orders each page by its declared watermark and unique
tie-breaker. Its checkpoint advances only after durable downstream
acknowledgement, so replay is at least once. The declared snapshot barrier is a
restriction, not permission to replace an invalid state with a full scan. A
poll cannot observe a hard delete after the row disappears; delete-aware history
needs a declared cursor-advancing soft-delete mapping. State incompatibility,
source identity mismatch, snapshot expiration, and retention failures require
an explicit rebootstrap.

Use `pm connectors inspect <name> --json` and `pm connectors catalog --json`
to see a connector's static polling-watermark declaration status, not
object-and-destination eligibility. A planned, unsupported, or absent static
declaration alone is not an executable polling mode. A connector that constructs
an implemented declaration per selected catalog object can become eligible only
after the same runtime preflight succeeds.

## Running an extraction

```bash
pm etl run --connection <name> --stream <stream> [--batch-size <n>] [--max-in-flight-batches <n>] [--json]
```

### Flags

| Flag | Required | Description |
|---|---|---|
| `--connection` | Yes | Name of the connection to use. |
| `--stream` | Yes | Stream within that connection to extract. |
| `--batch-size` | No | Records per write batch. Default is 1000. |
| `--max-in-flight-batches` | No | `1..8` only for a transformed `full_overwrite` Arrow transport when both endpoints declare ordered-pipeline support. The admitted default is `2`; `1` preserves serial callback behavior. Unsupported endpoints fail before I/O. |
| `--runtime` | No | After local ETL completes, record the run through optional PostgreSQL, DragonflyDB, and Temporal runtime checks. |
| `--json` | No | Emit structured JSON to stdout instead of human-readable text. |

### Example

```bash
pm etl run --connection my-github --stream issues --json
```

For tighter memory bounds on large streams:

```bash
pm etl run --connection my-github --stream pull_requests --batch-size 500 --json
```

For an eligible PostgreSQL transformed full-overwrite run, overlap the next
bounded source extraction with the current ordered COPY:

```bash
pm etl run --connection pg_snapshot --stream public.events \
  --max-in-flight-batches 2 --json
```

The depth is both a retained-batch and byte-credit bound. It preserves receipt
order and the single publish/read-back/checkpoint barrier; it neither creates
unordered work nor adds a second COPY worker.

For a `declarative_typed_destination`, `--destination-action` is the one stable
action identity persisted on the stream. It must name an action the destination
definition made eligible for the stream's mode; connection creation validates
that descriptor, source binding, acknowledgement, and registered executor
before any catalog or provider I/O. It is never accepted by `pm etl run`.

For runtime-backed recording:

```bash
pm runtime doctor --json
pm etl run --connection my-github --stream issues --runtime --json
```

## Closed GitHub issue-label transport

`github-issue-label` is deliberately a closed two-action GitHub label
destination, not a generic writer. Its saved connection owns the repository,
source selection, target issue, label, action, and credential configuration.
The destination's `sync_transport.json` declares each admitted source executor,
eligible source streams, and its bounded record mapping. The command accepts
none of those provider details as flags.

The declared `config_match` binding retains the one-record issue selection;
the `input_fields` binding maps each durable reopened PostgreSQL row's
`target_issue` and `label` fields into the exact input names declared in
GitHub's `transport_binding`. `full_append` maps to `add_issue_labels`;
`incremental_upsert` maps to `set_issue_labels` and requires
`transport_allow_keyed=true`. The mapped values must equal the plan-bound
destination configuration. Null, malformed, mismatched, or tombstone/delete
rows are rejected before GitHub write I/O. This singleton destination requires
`--batch-size 1`.

Create a plan, preview it in human output, and pass the resulting one-time
approval token only through standard input to the ordinary ETL run:

```bash
pm etl transport github-issue-label plan --connection transport-demo --json
pm etl transport github-issue-label preview <forward-plan-id>

pm etl run --connection transport-demo --stream <stream> --batch-size 1 \
  --approval-plan <forward-plan-id> --approval-token-stdin \
  --confirm destructive --json
# Paste the previewed token as the one stdin line, press Return, then EOF.
```

The forward run remains the normal closed path: GitHub or PostgreSQL source
read, durable connection-owned WAL/DuckDB/Parquet stage, independent reopen,
typed label mutation and durable acknowledgement, independent provider
read-back, then checkpoint.
The raw token is never accepted in argv, environment variables, files, JSON
output, or persisted project state.

After that first approved non-additive run, an identical-scope run reuses the
durable authorization by supplying the same `--approval-plan` and
`--confirm destructive` without `--approval-token-stdin`. A changed, expired,
or revoked scope is refused before a provider write. Cleanup always remains a
separate plan with a fresh one-time stdin token.

GitHub source selection and every independent provider read-back inspect only
the first GitHub issues page. If the configured GitHub source or target issue
is not present, the run fails rather than requesting a second page.

Cleanup is separately planned and approved; it cannot reuse the forward token:

```bash
pm etl transport github-issue-label cleanup plan \
  --connection transport-demo --forward-plan <forward-plan-id> --json
pm etl transport github-issue-label preview <cleanup-plan-id>

pm etl transport github-issue-label cleanup run <cleanup-plan-id> \
  --connection transport-demo --approval-token-stdin \
  --confirm destructive --json
# Paste the previewed cleanup token as the one stdin line, press Return, then EOF.
```

The cleanup action is the fixed typed `remove_issue_label` inverse. A declared
GitHub missing-label `404` is accepted as an idempotent cleanup; replaying a
consumed approval is rejected before another provider request.

## Declarative typed destination transport

`declarative-typed-destination` makes a connector-owned reverse-ETL action
reachable through the ordinary persisted connection path. The destination must
declare `declarative_typed_destination` in `sync_transport.json`; the saved
stream's `destination_action` is the stable identity for one exact eligible
`writes.json` action. If one connector declares two record-driven destination
actions for the same mode, each needs its own persisted selection. Declaration
order never selects a provider action.

```bash
pm etl transport declarative-typed-destination plan \
  --connection <name> --stream <stream> --json
pm etl transport declarative-typed-destination preview <plan-id>

pm etl run --connection <name> --stream <stream> --batch-size <n> \
  --approval-plan <plan-id> --approval-token-stdin \
  --confirm destructive --json
```

The commands do not accept a connector, action, URL, HTTP method, body,
mapping, or evidence override. Those remain connector JSON behavior. The
shared application layer validates the sealed execution descriptor, bounded
source mapping, approval, workset ownership, durable
acknowledgement, and read-back. Wrong-mode, missing, malformed, or cross-
connector declarations fail before provider I/O.

Plan and preview output list and digest-bind every declaration-owned physical
action, including any independently destructive tombstone delete. The runtime
may clamp `--batch-size` to the selected action's acknowledgement, read-back,
and bounded private-receipt capacity; it never creates a larger provider
mutation unit. A tombstone is a separately approved tombstone delete with a
distinct mapping, idempotency key, and independent absence read-back before
checkpoint.

### Complete reverse-ETL result output

For a completed declarative typed destination, `pm etl run --json` and
`pm etl status --json` include `run.destination_results`. Each item preserves
the selected named action's record accounting and complete successful provider
response: status, headers, and body. The CLI does not discard ordinary response
fields because they are rare, destructive, paid-tier-specific, or unfamiliar.

Provider-returned fields, keys, and values are preserved verbatim, even when
they equal configured credential bytes. System-generated plans, logs, request
diagnostics, and synthetic errors remain secret-taint-safe. If a later local
receipt, acknowledgement, composition, or output step fails before checkpoint,
the persisted failed run still retains ordered sanitized provider evidence. The
same preserved-result contract is used by persisted regular reverse-ETL runs
(`destination_result`) and direct-write run output.

If a closed transport already applied, read back, and checkpointed a provider
effect but local receipt retirement or a declaration-owned approval marker
cannot finish, the persisted run is terminal with status
`delivered_reconciliation_required`. Its `delivery_reconciliation` field names
only the bounded local repair and its `destination_results` and checkpoint stay
intact. The nonzero JSON response contains that exact `ETLRun`; repeating the
same saved connection and stream repairs from durable state before endpoint
resolution and never replays source or destination I/O. Missing, malformed, or
stale reconciliation evidence remains refused rather than falling back to an
ordinary route.

## Closed PostgreSQL managed-target transport

`postgres-managed-target` is a fixed definition-selected source-to-PostgreSQL
route, not a generic SQL writer. The saved connection owns both credentials,
the source stream and sealed schema, primary key, mode, and immutable managed
destination identity. PostgreSQL sources use their typed relation catalog;
declared API sources use their authoritative JSON stream schema.

Create and preview a plan, then pass its one-time token only through standard
input to the ordinary ETL run:

```bash
pm etl transport postgres-managed-target plan \
  --connection <name> --stream <stream> [--authorization-lifetime <24h..48h>] --json
pm etl transport postgres-managed-target preview <plan-id>

pm etl run --connection <name> --stream <stream> \
  --batch-size 1000 --approval-plan <plan-id> \
  --approval-token-stdin --confirm destructive --json
```

The registered source stages each bounded page in the connection-owned
warehouse. The registered destination reopens the sealed Parquet, derives an
immutable workset, applies it through the native managed target, independently
reads back the durable receipt, and only then advances the source checkpoint.

For an `incremental_upsert` PostgreSQL source, set `transport_bootstrap=true`
on the source credential to start with a gap-free snapshot barrier and continue
into committed `pgoutput` transactions. A fresh process resumes from the
acknowledged LSN. Planning binds the sealed source schema and both credential
revisions. The one-time preview token creates a durable, revocable authorization
with a 24h default lifetime (configurable from 24h through 48h at plan time).
Each provider page fetch and staged PostgreSQL apply has its own bounded
deadline, so a stalled unit stops without expiring the overall authority. Stale,
replayed, authentication-refused, and permission-refused runs do not advance the
checkpoint. PostgreSQL publishes this managed warehouse-mediated
destination only through its closed `destination_transport` declaration:
`write=false` remains the truthful public capability because direct
`Connector.Write` is unavailable. The route accepts no raw SQL or
caller-selected target identifiers.

## Checking run status

Each successful `pm etl run` produces a run ID. Use it to retrieve status later:

```bash
pm etl status <run-id>
```

```bash
pm etl status <run-id> --json
```

<Callout type="info">
  The run ID appears in the JSON `run.id` field and in the plain-text output line. Store it if you need to poll for completion in a script or agent.
</Callout>

## Inspecting the catalog

Before running an extraction, you can discover the streams a connector exposes:

```bash
pm catalog refresh --connection <name>   # fetch the latest connector catalog
pm catalog show   --connection <name>   # display the cached catalog
```

For a connector with provider-discovered fields, `pm catalog show` makes an
expired snapshot explicit. Run `pm catalog refresh --connection <name>` before
depending on a newly added provider field; cached schemas are never silently
presented as current.

## Exit codes

Agents and scripts should branch on exit codes, not parse stderr text.

| Code | Meaning | Recommended action |
|---:|---|---|
| `0` | Success | Continue. |
| `2` | Usage error | Fix the command invocation -- do not retry. |
| `3` | Validation error | Fix the argument values -- do not retry. |
| `4` | Auth error | Surface to a human to add or update credentials. |
| `5` | Connector error | Inspect the error detail; may be retryable. |
| `6` | Runtime unavailable | Start the required dependency (DuckDB, Postgres, etc.). |
| `7` | Policy refusal | Resolve the declared safety or authorization policy; do not retry unchanged. |
| `1` | Internal error | File a bug report. |

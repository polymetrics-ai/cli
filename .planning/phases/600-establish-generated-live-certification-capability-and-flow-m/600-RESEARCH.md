## Chosen design

### Capability artifact

`internal/connectors/certifications/capability-matrix.json` is a deterministic,
generated artifact. A `connectorgen certification-matrix` command regenerates
it; `--check` compares regenerated bytes to the committed result and fails on
any source or artifact drift.

The generator parses Go source to discover capability fields and operation
kinds. Real engine executor functions carry a narrowly scoped source annotation
that the parser can associate with the declared operation kind. This is not a
second taxonomy: a newly added `expectedOperationBlock` case still produces a
row automatically; without a real executor annotation it is truthfully
implemented=false and causes artifact drift until regenerated.

Every connector has one cell per discovered kind. A cell is either applicable
or holds a reason object with a non-generic code and explanation. Applicable
cells carry declared, implemented, fixture-tested, live-tested, fixture
evidence, and accepted live-evidence pointers. `live_tested` is false by
default and can only become true through a strict record under the new accepted
evidence namespace. Existing bundle `certification.json` files and fixture
filenames are not read as live evidence.

`capability_complete` is true only when at least one cell is applicable and
every applicable cell has all four required booleans true. This is a progress
fact, not the final flow-aware certification result.

### Pair-flow artifact

`internal/connectors/certifications/flow-matrix.json` is generated in the same
command and drift check. It contains explicit per-connector roles
(`api_source`, `api_destination`, `database_source`, `database_destination`),
including a named reason whenever a role cannot apply. This makes, for example,
an API connector's inability to be a database destination a machine-readable
fact instead of an omitted row.

A flow is identified by `(flow_kind, source, destination)`. To avoid an
unreviewable cartesian-product file, the serialized matrix uses disjoint
source/destination set products with a default pair cell and pair-specific
overrides. The resolver and validator treat every member of a set product as
an individual pair cell; an accepted evidence record names both endpoints and
can only alter that exact pair. The baseline still reports exact pair counts
per API-to-API, API-to-database, database-to-API, and database-to-database
kind.

Flow evidence must be pair-scoped and include an independent destination
readback reference. Endpoint-level evidence cannot substitute for it. A
connector's final `certified` result requires both capability completeness and
every applicable pair cell involving it to be complete.

## Evidence safety

- No provider calls, credentials, or inferred live results are used while
  generating the baseline.
- Accepted evidence is schema-validated, source-controlled, and constrained to
  the certification evidence directory. It requires a named provider/instance,
  timestamp, bounded pointer, passed status, and, for flows, a destination
  readback pointer.
- A malformed, missing, generic `n/a`, or generic `blocked` reason is an
  error. It never silently turns a requirement into non-applicable.
- Generator inputs are read beneath the repository root; output paths are
  fixed. This avoids user-controlled path traversal while retaining a
  reproducible developer command.

## Verification strategy

1. Write RED tests for source discovery, supported executor annotation,
   PostgreSQL/MySQL write stubs, certification completeness, named N/A reasons,
   strict live evidence, and generated-byte drift.
2. Implement the capability model and deterministic writer, run focused
   `cmd/connectorgen` tests, then commit the capability artifact separately.
3. Write RED tests for pair identity, role reasons, durable-destination
   admission, readback-required flow evidence, and pair-artifact drift.
4. Implement compact pair flow sets and final certification aggregation, run
   focused tests, generate the second artifact, and commit it separately.
5. Run generation checks, relevant package tests, the individual verification
   gates required by `AGENTS.md`, then execute inline verification and review.

## Docs/CLI parity assessment

The change adds only `cmd/connectorgen`, a developer-only generation command;
it changes no `pm` command, help topic, user-facing documentation, or website
surface. The CLI help/docs/website parity checklist is therefore explicitly
not applicable. The command's own usage text and an architecture document are
in scope.

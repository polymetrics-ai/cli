# Cutting a pm release

This is the maintainer procedure for publishing `pm`. For the commands that
verify checksums, Cosign bundles, GitHub attestations, Linux packages, and the
Homebrew notification, use [Release verification](release-verification.md).

## The release trigger

The supported release trigger is merging the Release Please pull request named
`chore: release <version>` into `main`. Release Please creates or updates that
pull request after release-worthy commits reach `main`. Merging the release pull
request creates the `v<version>` tag and published GitHub release; the remaining
jobs build and attach its artifacts.

These actions do **not** choose or cut a release:

- merging an ordinary feature or fix pull request only makes that commit an
  input to the next Release Please calculation;
- running the workflow manually only asks Release Please to recalculate its
  state; it is not a “release this version” control;
- editing `.release-please-manifest.json`, choosing a version by hand, or
  creating a tag or GitHub release manually is not part of the release process.

The workflow also listens for `release: published`. That event provides an
idempotent packaging path for an already published canonical `vX.Y.Z` release
and a recovery run for the release created by Release Please. It does not
replace the generated release pull request as the version-selection and
publication gate.

## How the version is derived

[`release-please-config.json`](../release-please-config.json) configures the
repository as one Go package named `pm`; the current released version is tracked
in [`.release-please-manifest.json`](../.release-please-manifest.json). Release
Please derives the next version from Conventional Commit messages since that
version. Do not hand-pick it.

The release-driving commit forms are:

| Commit form | Version effect |
| --- | --- |
| `fix:` or `fix(scope):` | patch |
| `perf:` or `perf(scope):` | patch |
| `feat:` or `feat(scope):` | minor |
| `type!:` or a `BREAKING CHANGE:` footer | breaking |

The highest required bump wins. Other prefixes such as `docs:`, `ci:`, `test:`,
`refactor:`, and `chore:` categorize a change but do not request a release by
themselves.

Feature commits normally advance the minor version. The enabled
`bump-minor-pre-major` option additionally makes a breaking change advance the
minor version rather than the major version before `1.0.0`. Thus both are minor
bumps while `pm` is pre-1.0. For example, if the manifest contains `0.1.1` and
the eligible history contains any `feat:` commit, the generated release is
`0.2.0`, not a manually selected version.

[`scripts/release-please-pm-filter.py`](../scripts/release-please-pm-filter.py)
builds the history used for the PM calculation. A commit that changes only
`website/**`, `.github/workflows/website.yml`, or `.gitlab-ci.yml` is omitted, so
a website-only change cannot create or enlarge a PM version bump. A commit that
also changes PM files remains eligible.

## Before merging the release pull request

Check all of the following:

1. The pull request was generated by Release Please, targets `main`, and has the
   configured title `chore: release <version>`.
2. The proposed version matches the eligible Conventional Commits. In
   particular, confirm the pre-1.0 minor-bump rule and that website-only commits
   did not affect the result.
3. The manifest and changelog changes describe the intended release. Do not
   “correct” the version by editing it manually; correct the commit history or
   Release Please configuration and let the pull request regenerate.
4. Required pull-request checks and review are green. The release workflow's PR
   path natively builds both Linux architectures, assembles snapshot archives
   and packages, and installs the `.deb` and `.rpm` packages under QEMU.
5. The release workflow and packaging files contain no unrelated changes. A
   release pull request is a publication gate, not a place to repair release
   machinery.

Merge the release pull request only after those checks pass. The merge is the
irreversible publication decision.

## What runs after the merge

The jobs in [`.github/workflows/release.yml`](../.github/workflows/release.yml)
run in this order:

1. **`release-please`** runs on the push to `main`. It calculates from the
   filtered PM history, creates or updates the release pull request when one is
   needed, and—when the merged commit is that release pull request—creates the
   tag and published GitHub release.
2. **`release-binaries`** starts when Release Please reports that the PM CLI
   release was created, or in a `release: published` run. It checks out the
   release tag and builds `pm` natively with cgo on four runners:

   | Target | Runner |
   | --- | --- |
   | `linux/amd64` | `ubuntu-latest` |
   | `linux/arm64` | `ubuntu-24.04-arm` |
   | `darwin/amd64` | `macos-13` |
   | `darwin/arm64` | `macos-latest` |

   Each build uses `go build -trimpath` and `-ldflags "-s -w ..."`; the
   additional linker assignments record the release version, commit, and build
   date. The native binaries are uploaded as one-day GitHub Actions artifacts
   for the next job.
3. **`release-assets`** downloads those four binaries, creates four `.tar.gz`
   archives plus amd64/arm64 `.deb` and `.rpm` packages, writes
   `checksums.txt`, generates GitHub SLSA attestations and keyless Cosign bundles,
   verifies the complete set, and uploads the verified files to the published
   GitHub release. If the exact verified asset set is already present, it
   verifies and reuses it rather than overwriting it.
4. **`notify-homebrew-tap`** runs only for `polymetrics-ai/cli`, the `pm-cli`
   release component, and a successfully verified asset set. It currently sends
   the Homebrew formula update request in dry-run mode.

The published archives, packages, checksum manifest, and Cosign bundles land on
the GitHub release for `v<version>`. GitHub stores the provenance attestations
against those subjects. Follow [Release verification](release-verification.md)
to validate the final release; that page is the source of truth for the trust
evidence and Homebrew checks.

## Recovering a partial failure

Do not create a replacement tag, edit the version manifest, or merge another
release pull request for the same version.

1. Open the Actions runs for the release commit. A normal Release Please
   publication can produce both the original `push` run and an idempotent
   `release: published` run.
2. Identify the first failed job and preserve its logs. Fix release machinery in
   a normal pull request if code or configuration is wrong; do not patch the
   published tag.
3. For a transient failure, use GitHub Actions **Re-run failed jobs** on the
   `release: published` run. Its event payload retains the published tag, and
   the asset job refuses to overwrite a mismatched set while accepting an exact,
   already verified set.
4. Re-run promptly: intermediate binary artifacts have a one-day retention.
   If they have expired, use **Re-run all jobs** on the `release: published`
   run so the release binary matrix runs before the asset job.
5. If the release contains only part of the expected asset set, the workflow
   deliberately stops with “unexpected assets” instead of overwriting it.
   Compare the release against the expected names printed by
   `scripts/verify-release-assets.sh --release-version <version> --print-expected-release-assets`.
   Stop and obtain a maintainer incident decision before deleting anything.
   With that approval, remove only the confirmed partial, unverified uploads,
   then re-run all jobs on the `release: published` run. Never remove or replace
   an asset that has already been distributed without an incident decision.
6. Finish by running every check in
   [Release verification](release-verification.md). A published tag without the
   complete verified asset set and successful downstream notification is a
   failed release, not a completed one.

## Checked-in sources of truth

- Trigger, job conditions, runners, build flags, asset upload, and retry-safe
  checks: [`.github/workflows/release.yml`](../.github/workflows/release.yml)
- Package name, release type, title, changelog, and pre-1.0 bump policy:
  [`release-please-config.json`](../release-please-config.json)
- Current released version: [`.release-please-manifest.json`](../.release-please-manifest.json)
- Eligible history and Conventional Commit bump detection:
  [`scripts/release-please-pm-filter.py`](../scripts/release-please-pm-filter.py)
- Archive/package assembly, expected asset names, and deterministic archive/
  installed-binary byte-budget reports:
  [`scripts/assemble-release-assets.sh`](../scripts/assemble-release-assets.sh),
  [`scripts/verify-release-assets.sh`](../scripts/verify-release-assets.sh), and
  [`scripts/verify-release-size-budget.sh`](../scripts/verify-release-size-budget.sh)
